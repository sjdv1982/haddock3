# A witness-centered test class system for HADDOCK3

Generated by Claude (Opus 4.8) following discussion with Sjoerd

*Status: draft for discussion. This document proposes a systematization of the
HADDOCK3 test suite and classifies the current non-workflow tests (unit +
integration) against it. It builds directly on two companion documents:*

- [docs/architecture.md](../architecture.md) — the feature map this document
  classifies against (modules, gears, libs, CLIs, the CNS-job granularity).
- [docs/testing/witness_coverage_assessment.md](witness_coverage_assessment.md)
  — the coverage gap this system is meant to close. That document's three
  "levels" map onto the property ladder below: its level 1 = *smoke*, level 2 =
  *witness-correct on fixed input* (A-calc / A-module), level 3 =
  *workflow/ensemble acceptance* (F).

It is a **draft**: the class definitions are settled in principle, but the
per-feature verdicts, bands, and priorities are for review.

## Addendum: independent review


Author: Codex (5.5 high)

An independent re-reading of the architecture and test tree broadly agrees with
this document's central diagnosis:

- the suite is broad on feature reachability and plumbing;
- it is relatively strong on pure witness calculators, such as CAPRI metrics,
  RMSD-related logic, parsing, scoring arithmetic, and clustering helpers;
- it is weak on fresh CNS-artifact witnesses, such as generated PDB energies,
  generated HADDOCK scores, and scoring TSV values compared against curated
  baselines;
- it is essentially missing workflow/ensemble witness acceptance, such as
  top-N distributions, best-cluster quality, CAPRI-star distributions, and
  score/RMSD/DockQ distributions;
- `examples/compare_runs.py` is a useful proto-version of workflow witness
  comparison, but it is manual/run-to-run rather than a curated gate/review
  witness system.

The review also supports one of this document's important methodological
claims: classification should be by assertion, not by file or directory. For
example, `integration_tests/test_emscoring.py` mixes P-style assertions such as
"file exists" with weak A-style assertions such as `score < -10` or
`fnat ~= 0.95`.

Several qualifications should be kept in mind when using the tables below:

- "No test at any level" is too strong for modules such as `cgtoaa` and
  `seletop`, which are exercised by end-to-end workflows as smoke/reachability
  checks. A more precise statement is: no direct unit/integration witness tests,
  only incidental workflow smoke coverage. For `lightdock` and `openmm`, the
  no-meaningful-test-coverage claim is much closer to true.
- `integration_tests/test_cnsjob.py` is a good CNS execution harness, but not
  yet a direct A-job witness harness for HADDOCK science. The current CNS input
  mainly writes coordinates with a seed; it is not obviously a representative
  `emscoring`, `rigidbody`, or refinement job that emits HADDOCK energy
  headers. Turning it into an A-job witness test may require changing or adding
  a fixture CNS input that produces meaningful HADDOCK energies.
- "Every module should have a single-job and ensemble witness test" is best
  read as an aspiration where semantically applicable. For modules such as
  `exit`, `filter`, `seletop`, topology generators, or format-conversion
  modules, the right witness may be selection integrity, propagated metadata,
  topology validity, or downstream score preservation rather than a CNS
  single-job witness.

On the merits, the class system is judged to be a strong basis for
implementation. The feature-by-property matrix is the right mental model; the
P/A/B/F separation maps well onto HADDOCK3's architecture; and the
A-calc/A-job/A-module split is especially useful for a granular execution-cache
or Seamless porting plan. Treating gate vs review as a per-cell policy is also
cleaner than turning those policies into separate classes.

Suggested refinements before treating the taxonomy as settled:

- add a short glossary and define terms such as `A0` before using them;
- state explicitly that some witnesses are artifact-validity or conservation
  witnesses, not scientific quality metrics;
- distinguish direct tests from incidental end-to-end smoke coverage in the
  module-gap table;
- avoid under-valuing B invariants, which are cheap and useful for trusting
  derived witness tables;
- do not treat caching only as a Seamless-specific concern: reliable caching
  could make much broader example-based regression testing practical by
  amortizing expensive CNS work. Cache hit/miss and dependency-sound checks are
  therefore both cache-trust tests and enablers for turning more of `examples/`
  into routinely executable witness tests.

Bottom line: the conclusions are sound, and the taxonomy is good enough to
guide implementation. It mainly needs a little sanding to avoid overclaiming
coverage holes or forcing the same witness shape onto every module.

## 1. The model: two axes, one cell per test

Coverage is a **matrix of features × properties**. A single test occupies one
cell. The current suite is wide on features and shallow on properties:
**reachability ≈ all, correctness ≈ smoke.**

### 1.1 The property ladder (rows)

Properties are distinct questions, in increasing strength. The **witness line**
separates ordinary software testing (below) from the witness initiative (on and
above).

| Property | Question | Class | Goal |
|---|---|---|---|
| Reachable / **smoke** | runs, emits expected files? | — | — |
| **Plumbing-correct** | format / parse / params / job-construction right? | **P** | — |
| ── witness line ── | | | |
| **Witness-correct** | right scientific value vs baseline (± band)? | **A** | G2 (anchors G1) |
| **Consistent** | internal cross-artifact invariants hold? | **B** | — |
| **Reproducible** | same result under irrelevant change; cache **hit ≡ miss**? | (invariance) | **G1** |
| **Dependency-sound** | a *relevant* change correctly forces a cache **miss**? | (cache) | **G1** |
| **Regression-bounded** | full-pipeline witnesses within bands? | **F** (gate) | G2 |
| **Acceptable** | meets scientific quality (human / success-rate)? | **F** (review) / benchmark | G2 |

G1 = the native CNS caching goal (prove synthesized reference equivalence for
content-addressed transformations). G2 = the CNS-alternative goal.

**The within-execution spine is free and nested:**
`exists ⊂ parses ⊂ witness-in-band ⊂ tighter-band ⊂ R1-checksum`. All rungs are
evaluated on one produced artifact; the strictness "dial" is simply *which rung
gates*. **B** is a parallel rung (one artifact, a different question — an
invariant, not a tighter tolerance). **Reproducible / dependency-sound** cost
extra *executions* (run cache-on/off; perturb a dependency). **F** costs a
different *harness* (a full run) — it is a new test, not an upgrade of an A test.

### 1.2 The classes

- **A — isolated witness correctness.** Single controlled input, fixed
  seed+env, golden witness. Three granularities:
  - **A-calc** — a pure-Python witness *calculator* on a fixed input
    (RMSD/align, FCC, CAPRI metrics, `HaddockModel` score arithmetic).
  - **A-job** — one CNS subprocess (`CNSJob`) → witness. **This is the Seamless
    cache unit** ([architecture §8](../architecture.md): "this per-model job is
    the natural unit for any future caching scheme").
  - **A-module** — a `HaddockModule` (CNS or pure-Python) → witness.
- **B — internal-consistency invariants** (e.g. `capri_clt` mean equals the mean
  of the top-N `capri_ss`; table score equals the weighted sum of PDB energies).
  Deprioritized; cheap where definitional.
- **F — full-run witness test** (one workflow via `H-run`, fixed seed,
  committed reference). Per-step witnesses over a real workflow; R3
  (distributional) bands are unavoidable at this scale. Each **cell** carries a
  policy:
  - **gate** — the witness has a locked band → automatic PASS/FAIL, blocks merge;
  - **review** — no defensible band yet → report-only; a human reviews the diff
    and `bless`es or fixes.

  One real run mixes both (a banded `topoaa` step gates; an un-banded
  ensemble-quality witness is reviewed). The policy field **is** the lifecycle:
  locking a band flips a cell `review → gate`. *(This single class replaces the
  earlier split into "C" automatic and "D" human-reviewed: they differed only by
  whether a cell had a band, which is already a per-cell attribute. "gate"/
  "review" survive as per-cell markers — e.g. `@gate`/`@review` — that drive CI
  routing, not as separate classes.)*
- **P — plumbing / non-witness software.** Config, parsing, params, CLI,
  schedulers, validation, I/O, job *construction*, file-existence. Most of the
  current suite. Stays as-is; its applicable ceiling is plumbing-correct.
- **benchmark** — many-seed success-rate validation. Out-of-suite, periodic.

### 1.3 Harnesses, the golden file, regimes (recorded for reference)

- **Harnesses** (execution): **H-job** (one `CNSJob`) · **H-module** (one
  `HaddockModule`, mock IO) · **H-run** (a workflow). A/B reuse H-job/H-module;
  F uses H-run. All share one **evaluation library** (witness extractors +
  three-layer comparator + report/bless).
- **Three-layer golden file**: *data* (witness values or canonical checksums +
  provenance) / *policy* (bands, regime parameter) / *mechanism* (extractors,
  the derived-mode rule, comparators, the always-on side-by-side report). The
  comparison **mode is derived** from provenance, not stored.
- **Reproducibility regimes**: **R1** bitwise → checksum; **R2** witness-tolerant
  → value ± band; **R3** distributional → distribution + margin. Measured per
  (feature, engine, env), not asserted. Ensemble tables hold the (R2/R3)
  witnesses; per-structure PDBs are kept as **checksums** (R1 same-provenance
  integrity trip-wire), not as scientific witnesses.

### 2.5 A-job — the cache unit (verdict: harness present, witness absent)

`integration_tests/test_cnsjob.py` (7 tests, **sci 0**) already **is the A-job
harness**: it runs a single `CNSJob` from a frozen `.inp`, with a **pinned

+ three-layer comparison turns it directly into the A-job correctness test — and
then the four cache-validation variants (correctness, reuse-foreign R1 integrity,
cache-disabled recompute, negative dependency-busting) attach here. **This is the
smallest, highest-leverage starting point for G1.**

## 3. Verdict: how much witness spine is present?

- **Below the witness line (P): well covered.** Config, params, IO, schedulers,
  CLIs, registry, restart/extend, job *construction* — all have real tests. This
  is the "feature coverage = all" that is genuinely complete *as plumbing*.
- **A-calc: surprisingly good.** Pure-Python calculators (CAPRI, RMSD/align,
  clustrmsd, alascan, contactmap, prodigy, ilrmsd) carry real fixed-value
  witness checks. The assessment's level 2 is largely met.
- **A-module on CNS artifacts: weak.** The exact gap the assessment names. CNS
  scoring/refinement tests use coarse, *guessed* bands (`score<-10`,
  `fnat≈X±0.1`); `topoaa` and `rigidbody` are **pure smoke**. No test pins
  CNS-embedded energies / HADDOCK score from a fresh artifact.
- **A-job: harness only**, no witness.
- **B: incidental.** One real instance (`_check_means_match`).
- **F: absent as witness.** End-to-end and `full_workflow` are smoke;
  `examples/compare_runs.py` is a manual run-to-run proto-F (review-style).

**Upgrade ease.** Most witness-bearing tests upgrade **in place along the free
spine** (route asserts through the evaluation library; replace guessed bands with
A0-calibrated R2; add the R1 checksum trip-wire). The exceptions that need *new*
artifacts/baselines: `topoaa`, `rigidbody` (smoke → witness), A-job, and all of
F.

## 5. End-to-end tests and examples → F (verdict: natural upgrade)

| Current | Shape | Target | Upgrade path |
|---|---|---|---|
| `end-to-end_tests/*.py` (4: protein-ligand, cg-scoring, molecules, protein-protein-shape) | full `cli_main` run, asserts folders/files exist | **F** (gate cells) | run H-run with a fixed seed → extract per-step witnesses → three-layer compare with R1/R2/R3 bands; gate on "any FAIL" |
| `integration_tests/test_full_workflow` | `WorkflowManager` run + `report.html` exists | **F** (gate cells) | same |
| `examples/*` + `examples/compare_runs.py` | real workflows; manual run-to-run CAPRI table diff (abs_tol 0.0011) | **F** (review → gate) | `compare_runs` logic becomes the report generator; commit reference witnesses + PDB-checksum trip-wires; `bless` to update; cells start as **review** and graduate to **gate** per-(example, engine) once bands stabilize |
| `examples/*` full-sampling, many-seed | — | **benchmark** | separate repo referencing `examples/`; success-rate stats; human-judged; out-of-suite |

The mapping is clean because F's cells differ only by *gate vs review* (band or
not), and the e2e/examples already perform the execution (`H-run`) — only the
assertion changes. `compare_runs.py` is the closest existing asset and becomes
F's comparator/report generator; caching (G1) is what makes a full-sampling F
suite over all of `examples/` affordable to run routinely.

## 6. Suggested first increments (derived, not new)

Ordered by leverage and by dependency (the evaluation library + A0 underpin
everything):

1. **Build the shared evaluation library** (witness extractors: `HaddockModel`,
   capri readers, RMSD/cluster; three-layer comparator; always-on report;
   `bless`). Keystone — every class reuses it.
2. **A-job on `test_cnsjob`**: add witness extraction to the existing seeded
   harness; then the four cache-validation variants. Smallest unit; directly
    validates the synthesized checksum reference (G1).
3. **A-module in place** on the CNS front, starting with `emscoring` (replace the
   guessed `±0.1` with an A0-calibrated R2 band + exact energies), then
   `mdscoring`/`flexref`/`emref`/`mdref`; close the `topoaa`/`rigidbody` smoke
   holes (needs new baselines).
4. **A0 as a mode of the same mechanism**: run a witness a few times under fixed
   code+seed+env, read the difference column → assign R1/R2/R3 and the starting
   band.
5. **Per-module ensemble tests** + the **missing-module** holes (`lightdock`,
   `cgtoaa`, `openmm`, `seletop`) — at least smoke first, witness where it
   applies.
6. **F** on `refinement` / robust e2e examples — gate cells where bands lock;
   promote `compare_runs.py` into F's report/`bless` path (review cells first);
   **benchmark** later, separate.

## Appendix: the witness/P line is per-assertion

Many files mix classes. `integration_tests/test_emscoring.py` asserts both file
existence (P) and `fnat≈0.95` (A-module). Classification is therefore by
**assertion**, not by file or directory — and the unit/integration/end-to-end
split (about *needs-CNS / speed*) is orthogonal to the A/B/F/P split (about
*what is asserted*). The upgrade work is: strengthen/add the witness assertions
via the evaluation library; leave the P assertions untouched.
